# Required phone —25 October2026

A phone is required on all public lead/contact surfaces: looking, homepage contact, property modal, and six neighborhood contact/modal pages. Existing native required attributes are retained and now paired with submission guards rejecting empty, whitespace-only and malformed values before fetch. Inputs announce their required status and use telephone keyboard/autofill. Error correction clears stale custom validity even on forms created after app initialization. Email remains optional. Existing Israeli-mobile rules remain on looking; contact forms accept local Israeli mobile/landline and explicit international formatting. This validates format, not number ownership.

The shared neighborhood contact renderer previously omitted the names expected by submitForm and assigned a string to the DOM onsubmit property. It now uses named fields and a real callback that prevents native form navigation before calling the guarded sender. This is needed for the required-phone behavior to work on those forms. No lead schema, permission, CRM data, provider credential or endpoint changed.

Office search intake already requires a valid Israeli mobile server-side.84 isolated local tests passed, including422/no contact/search/receipt/sends for absent or invalid phones. GET/preflight live checks are read-only; no live valid submission was sent. General/property contact still uses FormSubmit: this change enforces those forms in the browser and does not claim server-side provider enforcement or CRM integration for those contact types.

RED→GREEN: direct submit handlers previously called fetch for blank/invalid phones; dynamic rendered forms had unnamed fields and a nonfunctional string submit handler. Regression tests exercise the actual handlers/renderer with only transport replaced. Native Chrome checked empty, text, whitespace and correction on main contact, property modal, looking mobile and neighborhood contact. Local preview CSP blocks all external submissions.
